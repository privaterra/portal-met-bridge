# Protocol and integration notes

Collected while building portal-met-bridge, 2026-11-08. Everything below comes from the public repositories cited or from the author's own machine; the Portal BLE layout has been verified on hardware by the Decenza project, not by this project yet.

## Belka Portal (Bluetooth LE)

Source: [variegated-coffee/variegated-rs](https://github.com/variegated-coffee/variegated-rs), crate `variegated-belka-portal-trouble-driver` (MIT, Magnus Nordlander), mirrored by Decenza in `src/ble/protocol/belkaportalprotocol.h`.

- The Portal measures **electrical conductivity (EC) and temperature**, not refractive index. Belka's page lists EC as a "concentration indicator"; the companion app shows EC, temperature, flow and weight. There is no TDS in the protocol.
- One BLE central at a time: close the Belka phone app before connecting from elsewhere.

| Item | Value |
| --- | --- |
| Service | `0x7400` (16-bit UUID) |
| Measurement characteristic | `0x7410`, read + notify, **13 bytes** |
| &nbsp;&nbsp;bytes 0–3 | EC, `f32` little-endian, units presumed mS/cm |
| &nbsp;&nbsp;bytes 4–7 | internal temperature (?), `f32` LE |
| &nbsp;&nbsp;bytes 8–11 | outlet temperature °C, `f32` LE |
| &nbsp;&nbsp;byte 12 | status byte; looks like battery but semantics unverified, so shown raw |
| Command characteristic | `0x7420`, write **with response**, 4 bytes |
| Show graph on the Portal's screen | `40 00 01 2D` |
| Hide graph | `40 00 01 2E` |

The command bytes are written exactly as captured in Apple PacketLogger — they are *not* little-endian like the floats. The Portal acknowledges the write and never says whether it understood it.

Decenza's EC → TDS method (fork janhcla/Decenza, tag `portal-calibration-20261101`): mass-weighted integral ∫EC dm over cumulative cup weight; `meanEcPerG = ∫EC dm / covered mass`; proportional model `TDS% = k · meanEcPerG` with leave-one-out error; affine model only when it clearly wins; estimates flagged below 5 reference shots or outside the measured EC range; EC never presented as TDS without calibration; slow-wetting, thermal and gap gates exclude a shot from the reference set. `js/analysis.js` is an independent JavaScript implementation of the same idea.

## Meticulous (observed on firmware 0.2.24-475, image 2026M1510-beta)

Source: [MeticulousHome/meticulous-backend](https://github.com/MeticulousHome/meticulous-backend) plus the author's own machine on his LAN. The [nickwilsonr/meticulous-addon](https://github.com/nickwilsonr/meticulous-addon) README/code was the hint for the port.

- **Port 80.** nginx on the machine fronts the backend's REST and socket.io. The backend process listens on 8080 bound to `127.0.0.1`, so `:8080` is unreachable from the LAN. CORS is `*`, so a page on `http://localhost` can call the machine directly.
- socket.io `status` (~10 Hz): `{ name, state, extracting, time (ms since shot start, -1 idle), profile, profile_time, sensors: { p bar, f ml/s, w g, t °C, g gravimetric ml/s }, setpoints: { active, pressure?, flow? }, loaded_profile, id }`.
- socket.io `sensors` (same cadence): `{ t_ext_1, t_ext_2, t_bar_up, t_bar_mu, t_bar_md, t_bar_down, t_tube, t_motor_temp, lam_temp, p, a_0..a_3, m_pos, m_spd, m_pwr, m_cur, bh_pwr, bh_cur, w_stat, motor_temp, weight_pred, weight_kalman, weight_pred_kalman }`.
- Other events: `settings`, `notification`, `profile`, `profileHover`, `action`, `button`, `OSUpdate`, `calibrate`.
- `GET /api/v1/machine` → `{ name, hostname, firmware, mainVoltage, serial, color, batch_number, build_date, software_version, image_build_channel, image_version, repository_info{component:{branch,commit}}, version_history[], tare_behavior_supported, disturbance_resilience, pour_over_profiles_supported, … }`.
- `GET /api/v1/history/stats` → `{ totalSavedShots, byProfile: [{ name, count, profileVersions }], mileage }` (mileage = ESP lifetime counter).
- `GET /api/v1/history/last` → `{ id, db_key, time (epoch s), file, debug_file, name, profile_name, push_to_brew_time, profile{ id, name, temperature, final_weight, stages[], variables[], display{…} }, data: [{ time ms, profile_time, status, shot{ pressure, flow, weight, gravimetric_flow, setpoints{active,…} }, sensors{ external_1, external_2, bar_up, bar_mid_up, bar_mid_down, bar_down, tube, motor_temp, lam_temp, motor_position, motor_speed, motor_power, motor_current, bandheater_power, bandheater_current, pressure_sensor, adc_0..3, water_status, motor_thermistor, … } }] }`. ~7.5 samples/s. Stage names on the author's profile: `Saturate`, `Bloom`, `Gentle Rebuild`, `Extract`, then `retracting`. **The JSON contains bare `NaN` tokens** (seen in `sensors.motor_speed`); strict parsers must replace `: NaN` / `: Infinity` before parsing.
- `POST /api/v1/history` body `{ query, ids, start_date, end_date, order_by: ["date"], sort: "desc", max_results, dump_data }` → `{ history: [...] }`.
- `GET /api/v1/profile/list` → array of `{ id, name, author, author_id, temperature, final_weight, last_changed (epoch s), version, variables: [{ name, key, type, value }], display: { accentColor, description, shortDescription, image: "/api/v1/profile/image/<hash>.jpeg" } }` (stages omitted unless `?full=true`).
- `GET /api/v1/settings` → flat object: `enable_sounds, heat_on_boot, heating_timeout, auto_start_shot, auto_purge_after_shot, tare_behavior, disturbance_resilience, partial_retraction, update_channel, idle_screen, time_zone, clock_format_24_hour, ssh_enabled, usb_mode, profile_order[], …`.
- `GET /api/v1/wifi/config` → `{ config: { mode, apName, apPassword }, status: { connected, connection_name, gateway, routes[], ips[], dns[], mac, hostname }, health: { link_connected, has_ipv4, gateway_reachable, dns_resolves, internet_reachable, ap_active, degraded, message, … }, known_wifis }`. Note that `apPassword` is in this response — don't log it.
- `GET /api/v1/notifications`, `POST /api/v1/notifications/acknowledge`; `GET /api/v1/action/{start,stop,continue,preheat,tare,…}` (not used by this app).

## Beanconqueror hand-off

Source: [graphefruit/Beanconqueror](https://github.com/graphefruit/Beanconqueror) `docs/brew-import-api.md`.

- Deep link `beanconqueror://ADD_BREW?len=N&shareBrew0=…&shareBrew1=…` (batch: `ADD_BREWS`, ≤ 50 brews). Payload = `base64url(gzip(JSON))`, unpadded, split into 400-character chunks, ≤ 1,024 chunks, inflated ≤ 512 KiB per brew.
- Envelope v1: `app{name,version}`, `brew{date ISO, doseIn{g}, waterIn{ml} (required), beverageOut{g} (required), brewTime s (required), temperature °C, grindSize, grinderName, grinderRpm, preparationMethod (required), preparationType e.g. "METICULOUS", bloomTime, firstDripTime, rating 0–10, note}`, optional `bean{name, roaster, roastingDate, origin, …}`, `flow{fidelity full|downsampled, t[] delta ms, waterDispensed[] delta decigrams, weight[] delta decigrams, temperature[] absolute}`, `metrics[]{key, name, unit, kind measured|target, t[] absolute ms, v[]}` (≤ 100 metrics, ≤ 10,000 points each), `imported{source, sourceName, sourceUrl https, device, schema, params}` (required).
- **No TDS field.** The estimate goes in `brew.note` and `imported.params`; the EC trace is sent as a custom metric. Type the refractometer value into Beanconqueror's own TDS field for its EY.
- Beanconqueror has native Meticulous support (same socket.io `status` payload) and BLE refractometer support (DiFluid R2), but no Belka Portal support.

## Web Bluetooth on macOS Chrome (what the app relies on)

- `navigator.bluetooth.requestDevice({ filters: [{ services: [0x7400] }, { namePrefix: 'PORTAL' }, …], optionalServices: [0x7400] })` — filters are OR-ed; a 16-bit alias is accepted for the service. The variegated firmware and Decenza both identify a Portal by the advertised `0x7400`, so the service filter should match; the name prefixes are belt-and-braces (Decenza labels an unnamed Portal "PORTAL").
- `requestDevice` must run inside a user gesture (the Connect button) and shows Chrome's own chooser; nothing on the page can pick for you.
- `getAvailability()` returns false when Bluetooth is off **or** Chrome lacks the macOS Bluetooth permission; the Connection check surfaces this before the chooser.
- `writeValueWithResponse` is used for the 4-byte display commands (the Portal expects write-with-response).
- No background mode: notifications stop when the tab is discarded, so keep the tab open during a shot.
- `tests/fake-bluetooth.js` is a minimal stand-in for `navigator.bluetooth` that covers exactly this surface, useful for any other Portal tool written for the browser.

## Reviews in the report, continued reviews, stage verdicts, ratings (v0.17)

**The review in the PDF report.** `js/review-export.js` now exposes `pdfWriter(doc, { margin, bottom, y, footer })` — the block renderer the review PDF always used (headings, paragraphs, lists, tables, code, quotes, rules, with page breaks) — as a reusable writer with `.review(rev, { heading })`; `reviewToPdf` is that writer on a fresh document. `shotReportPdf(r)` (`js/export.js`) takes `r.review` and `r.reviewHeading`: after the notes it starts a new page and writes the review through the same writer with the report's margins, then numbers every page. `reportFor(...)` in main.js gets `review` from `reviewForShot(shotId, reviews)` — the newest saved review (`store.listReviews()` is newest first) whose `shotIds` includes the shot, with the heading "AI review of this shot (date · provider · model)" or "AI review of N shots including this one (…)" — and adds an *AI review* row to the metrics table (which review was appended, or *none saved*). Both the per-shot *Report (PDF)* button and the zip export pass it.

**Continued reviews.** A series review is longer than a single one and ran past the default output limit (OpenAI's chat endpoint got no limit at all, Anthropic/Gemini had a fixed 8 000), so the end of the report was missing. `maxTokensFor(shots)` in `js/ai.js` = 8 000 + 4 000 per extra shot, capped at 16 000 (under every current model's output ceiling), sent as `max_tokens` (Anthropic), `max_completion_tokens` (OpenAI — added to `OPTIONAL_PARAMS`, so an OpenAI-compatible server that rejects it gets the request once more without it) and `generationConfig.maxOutputTokens` (Gemini). `buildRequest` takes `history: [{ role: 'assistant' | 'user', content }]` appended after the first user turn (Gemini roles `model`/`user`). `finishFromEvent(provider, data)` reads the finish reason from the stream (`finish_reason: 'length'`, `message_delta.delta.stop_reason: 'max_tokens'`, `finishReason: 'MAX_TOKENS'`) and `finishFromResponse` from a non-streamed answer; `streamCompletion` calls `onFinish('length' | 'stop')`. In main.js `runReview` keeps the request in `an.request`, and `streamReviewPart(req, signal, sofar)` streams one answer into `an.markdown`; when it finishes with `length` the loop asks again with the text so far as the assistant's turn and "continue exactly where it stopped — no repeat, no preamble, mid-sentence if that is where it stopped" (at most twice on its own; `an.continued` counts, the status says "in 2 parts"); if the last part is still cut `an.cutOff` shows the *Continue the review* button (`continueReview()`), and the saved review is whatever is on screen. The mock machine's `cut-model` answers the first half with `finish_reason: 'length'` and, to a request carrying an assistant turn, the remainder from exactly that point, so the e2e can check the joined text equals the whole report.

**Stage verdicts.** Both templates' *Suggested changes* now begin with `### Stage by stage` — one bullet per stage in the order the machine ran them, "**stage** (from–to s): what happened — worked well | acceptable | needs work — what to change, or keep as is", quoting the stage's own numbers (across the shots in the series template) — followed by `### One change per shot` with the ordered single changes as before. `###` headings render as `h4` in the pane and at 12 pt in the PDF; nothing else changed in the parser.

**Rating and comment.** `shot.rating` (integer 1–5, absent when unrated; `ratingOf(shot)` in `js/review.js` validates) and `shot.comment` (trimmed, ≤ 2 000 characters). After a shot is saved `openRatingDialog(id)` runs — directly, or after the final-weight dialog closes when that mode is on (`pendingRating`) — unless `settings.askRating` is off; keys 1–5 set the stars, *Later* skips. `setShotRating(shot, rating, comment)` stores both, rewrites the automatic shot files, and re-renders the Shots header (`renderShotRating`: a star picker that saves on click, the comment, an *Edit comment* / *Rate this shot* link), History (`rating` column: `★4` with 💬 when a comment exists, tooltip with the words, sortable; the search covers the comment) and the Analysis picker and digest cards. The edit dialog has the same picker and a comment field. The digest carries `meta.rating` and `meta.comment` (null when absent), the series comparison lists `rating` per shot, in `steps` and in `trends`, and both templates tell the model to read them as the taste verdict and to say when the numbers disagree with it. `summaryRow` gains `rating` and `comment` columns, the PDF report a *Your rating* row and a *Your comment* note, and the Beanconqueror envelope its `rating` (1–5 passes the 0–10 contract) and a "Cup: …" note line. `num()` in `buildSeriesComparison` now keeps `null` as null (it used to turn a missing value into 0, which made "420 → 0 µm" out of a shot without a grind).

**Tagline.** "Meticulous & Belka Portal conductivity data visualization & analysis." in the header, `<meta name="description">`, About, package.json, the Home Assistant `config.yaml` and image label, the Info.plist (`CFBundleGetInfoString`) and the docs.

## Series reviews, https and the machine relay, the Home Assistant stop (v0.16)

**Series reviews.** With more than one shot `buildReviewMessages` switches to `REVIEW_TEMPLATE_SERIES` — every section compares (Shots compared · Stages with a column per shot · What stands out as one item per step 1 → 2, 2 → 3 … ending with "Trend:" · What helped and what did not · Suggested changes for the next shots built on the series) — and puts `buildSeriesComparison(digests)` ahead of the per-shot digests: one row per shot (setup, outcome, EC, TDS/EY, profile variables), `steps` between consecutive shots with every numeric delta and `setupChanged` (grind, dose, profile, setpoint, target, any profile variable), `stages` by name with a cell per shot (present/absent, times, water, cup, pressure, flow, EC share), `trends` per key (unchanged steps do not break a trend) and `notes` (different profiles, Portal data missing for some, more than one variable changed, no change at all). The earlier single template had only "Shots compared (only when more than one)", so the model compared in one table and reviewed the last shot.

**https and the relay** (`serve.mjs`). `TLS_PORT` + `TLS_CERT` + `TLS_KEY` start a second, https listener with the same handler (`TLS_SELF_SIGNED=1` only labels it); `GET api/cert` hands out the leaf certificate (never the key) so a self-signed one can be trusted on the computer; `api/server` gains `platform`, `tls`, `machineProxy`, `quitStopsApp`. `/machine/<host[:port]>/<path>` is relayed to `http://<host[:port]>/<path>` for REST (streamed, 15 s timeout, 502 with the reason) and for the WebSocket upgrade (the socket.io stream: the upgrade request is rewritten with the machine's Host and the bytes are piped both ways); `machineTarget()` accepts only private IPv4 ranges, `localhost`, `.local/.lan/.home/.internal` names and bare hostnames — not an open proxy. `js/meticulous.js`: `machineBaseUrl(host, { via })` and `new MeticulousClient(host, { via: 'server' })` build `<page origin>/machine/<host>` and connect socket.io with `path: /machine/<host>/socket.io`; main.js setting `machineVia` auto|direct|server, where auto = server when the page is https and the server advertises the relay (a secure page may not fetch the plain-http machine: mixed content). Why: Web Bluetooth needs a secure context, a LAN address is only secure over https with a trusted certificate, and a self-signed certificate with the warning clicked through does *not* count (powerful features stay off) — so the certificate has to be trusted on the computer once, and the page spells that out (`renderInsecureHint()`: the https link, the certificate download, the Keychain steps, and the chrome://flags alternative with the exact origin). The Home Assistant app serves 8787 http + 8788 https (`ssl: self-signed` makes a P-256 certificate on first start in `/data/tls` with SANs for the host names and the IP from `bashio::network.ipv4_address`; `home-assistant` uses `/ssl/<certfile>`,`<keyfile>`; `off`), needs `openssl` in the image and `hassio_api: true`.

**Stop in Home Assistant.** `ALLOW_QUIT=1` there, and `api/quit` with a `SUPERVISOR_TOKEN` in the environment calls `POST http://supervisor/addons/self/stop` (Bearer token) so Home Assistant shows the app stopped; if that fails the process exits as before. The dialog's last box is pre-ticked on that platform and worded for it.

**The my.home-assistant.io badge.** "Open page in your Home Assistant → refused to connect" means the instance address stored by that site in the browser (default `http://homeassistant.local:8123`) is not where Home Assistant is; documented in DOCS.md, README and PACKAGING with the manual route.

## Ready to brew, Stop, and two fixes (v0.15)

**Ready to brew** (`js/heat.js`, `HeatMonitor`). The status stream's `sensors.t` (and the `sensors` event's probes) are compared with the loaded profile's `temperature` — found by the status `id` in `state.profileList`, else by a unique name — under a rule from Settings → Machine: `machine` (the status name is "click to start"), `reach` (|T − target| ≤ tolerance now), `hold` (every sample of the last `holdSec` seconds inside the band, and the band entered at least that long ago), `settled` (hold, and max−min over the window ≤ `settleC`), `both` (machine and hold). The sample ring keeps 60 s (or holdSec + 5 s). Phases: `idle → heating → ready → brewing → done`; `extracting` puts it in `brewing` and **disarms** it, `done` stays plain however hot the water is, and it re-arms when the status name says heating again or the reading falls more than three tolerances under the target (a cold-start without the heating name). Changing the rule, the tolerance or the target clears the samples so a hold starts over. `renderHeat()` paints `#brew-start.ready` (green) and the `#brew-heat` line from `describe()`, and the Settings panel shows every sensor's current reading plus the verdict so the sensor can be chosen with the machine running. *Start brew* lost its `primary` class: plain like *Tare* unless ready. The mock machine ramps `dial.temp` from `tempFrom` to the loaded profile's temperature over `heatMs` with a 0.4 °C overshoot, holds ±0.1 °C at "click to start", and with `brewMs` > 0 runs a short extracting phase after the second click (`POST /mock/dial { heatMs, tempFrom, brewMs, temp }`).

**Stop** (top bar). `openStopDialog()` lists what runs; `stopEverything({ quitServer, abortBrew })` finishes a recording through `recorder.stopManual()` and waits for the `shot` event (so it is saved), aborts the AI stream, stops the live and replay loops, disconnects the Portal and the machine (`machinePanel.detach()`, `meticulous = null`, `heat.reset()`), clears the log-tail interval and the backup timer (running a last backup when one was pending), saves pending settings, flushes the log, and — when `GET api/server` said `quit: true` and the box was ticked — `POST api/quit`. `serve.mjs` answers `api/server` with `{ version, pid, dataDir, quit, local }` and honours `api/quit` only from a loopback address unless `ALLOW_QUIT=1`, never with `ALLOW_QUIT=0` (the Home Assistant app sets that: s6 would restart it). After the stop `#stopped` covers the page with the report; `state.stopped` silences the beforeunload warning and the machine-record attach.

**Review numbering.** `parseMarkdown()` ended a list at the first blank line, so a model writing numbered items a line apart (and most write "1." on every item, which Markdown allows) produced one `<ol>` per item, each starting at 1 — the ".docx/.pdf/text exporters number by position, so they showed the same. A blank line now continues the list when the next non-blank line is an item of the same kind at the same indent or an indented block of the current item; the template also asks for consecutive numbers outright.

**PDF report.** The two-column key/value table drew values at a fixed x with no width, so a long value ("43.0 g profile target (machine 20.1 g)") ran into the right-hand column. Keys and values are now wrapped with `splitTextToSize` to their cell widths and a row is as tall as its tallest cell; the charts are capped at 24 % of the page height (was 30 %) and the captions sit tighter, so a normal shot's report — two charts, both tables, the notes — fits one page instead of leaving a lone footnote on page two.

## Where files go (v0.14): downloads, a picked folder, or the server's data folder

Until v0.13 the only place files could land was a folder picked with Chrome's folder picker, under a fixed `portal-met-bridge/{shots,exports,reviews,backups,logs}` layout, and only the log and the automatic shot files went there unless "save exports to folder" was ticked; the folder had to be re-allowed after every Chrome restart, and nothing worked in Safari. v0.14 moves all of that into `js/files.js` (`files`, an EventTarget) with three **destinations** and one configurable **layout**:

- `downloads` — `download()` as before; nothing is written on its own.
- `folder` — the picked `FileSystemDirectoryHandle` (handle still stored under the IndexedDB setting `logFolderHandle`; `useFolder` / `pickFolder` / `forgetFolder` moved here from `log.js`). Nested paths are created with `getDirectoryHandle(p, { create: true })` per segment; appending seeks to `file.size` with `keepExistingData`.
- `server` — `serve.mjs` started with `DATA_DIR=<dir>` (or `--data`) answers `GET api/files` with `{ dataDir, host }` and accepts `PUT api/files/<path>[?append=1]` (streamed to disk, 512 MB cap) and `DELETE api/files/<path>` (recursive). `safeDataPath()` confines every path to the data folder: segments may not be `.`/`..`/empty/hidden and may not contain `\0`–`\x1f < > : " | ? * \`; the resolved path must stay under the folder. The URLs are relative (`api/files`, not `/api/files`) so the page also works behind a path prefix. `start.command`, the macOS app and the Home Assistant app all start the server with a data folder (`~/Documents/portal-met-bridge`, `/share/portal-met-bridge`); a plain `node serve.mjs` or Python's http.server answers 404 and the option is greyed out.

`fileDestination` = `auto` (default) resolves to a chosen folder first, then the server's folder, then downloads — so an upgrade keeps writing to the folder the user had picked, and a fresh install under the macOS app writes to Documents without any prompt. `effective`, `ready` (writable right now) and `blocker` (why not, for the status line) drive the UI; `write(kind, name, data, { append })` returns the path for notes and throws when nothing is writable, and `deliver()` falls back to a download on that. The layout is `fileRoot` (`portal-met-bridge`, blank = directly in the folder) plus `dirShots / dirExports / dirReports / dirReviews / dirBackups / dirLogs`, each passed through `cleanDirName()` (splits on `/` and `\`, drops `.`/`..`/hidden/empty parts and `<>:"|?*` and control characters, trims trailing dots and spaces, caps at 120 characters; an emptied subfolder falls back to its default); `rootInUse` drops the root when the destination is itself a folder of that name (`~/Documents/portal-met-bridge`, or a picked folder called `portal-met-bridge`), so nothing is nested twice. Per-shot chart JPEGs and the PDF report now go to `reports`, everything else keeps its kind. `eraseAll()` removes the root (or, with a blank root, only the known subfolders) at the effective destination — the Start-over wipe uses it.

The log no longer owns a folder: `log.setWriter(files)` and `flush()` calls `files.write('logs', 'YYYY-MM-DD.log', text, { append: true })`; lines queue (up to the ring size) while nothing is writable and flush when the destination becomes ready, so a log turned on before a folder is picked is not lost.

**Automatic backup**: `store.onChange(kind)` fires after every put/delete of a shot, bean, pick-list value or review and after an import; `scheduleAutoBackup()` debounces 12 s (so the two-second checkpoints during a live shot produce one backup after it ends) and `runAutoBackup()` writes `store.exportAll()` to `backups/portal-met-bridge-latest.json`, plus `portal-met-bridge-<date>.json` once a day (`lastDailyBackup` setting). It never downloads; with `downloads` as the destination it does nothing. The e2e test runs the server with a temporary `DATA_DIR`, switches the destination to it, exports a CSV, renames the root and the exports folder (with an escape attempt in the name), downloads the log, presses *Write a backup now*, and reads the files back from disk; it also PUTs `../x.txt`, `a/.hidden`, `a/..%2Fb` and `bad:name` straight at the API and expects 400s.

## File System Access API (log / export folder)

- `window.showDirectoryPicker({ mode: 'readwrite' })` needs a user gesture and Chrome/Edge; Safari and Firefox have no directory picker, so the app falls back to downloads.
- The returned `FileSystemDirectoryHandle` is structured-cloneable and is stored in IndexedDB; after a browser restart `queryPermission()` returns `prompt` and `requestPermission()` must again run inside a user gesture (the *Re-allow folder* button).
- Appending: `getFileHandle(name, { create: true })`, `createWritable({ keepExistingData: true })`, `seek(file.size)`, `write`, `close`. The log flushes every 3 s and on `beforeunload`.
- Removing the app's files: `folder.removeEntry('portal-met-bridge', { recursive: true })`; only that subfolder is ever touched. `BluetoothDevice.forget()` (Chrome 110+) drops the pairing permission; `indexedDB.deleteDatabase()` never settles while another tab holds the database open, so the wipe reports that case instead of hanging.
- `tests/fake-folder.js` stands in for all of this in tests.

## Settings save model (v0.7)

Before v0.7 every setting input saved on its `change` event, i.e. on blur. Typing an address and pressing Enter, reloading, or closing the tab never blurred the field, so the value was lost and the Shots-tab address kept the old value — the bug reported as "the machine address does not change on the main screen". There is no `<form>`, so Enter did nothing.

Now: toggles and `<select>`s still commit on change; text and number inputs are compared against the stored value on every keystroke (`dirtySettings()`), listed in the save bar, and committed only by Enter, ⌘/Ctrl+S, the Save button, or `showView()` leaving Settings (`saveAllSettings({quiet:true})`). `beforeunload` warns while something is pending. Every commit funnels through `flashSaved(keys)`, which keeps the keys saved during the current 4 s flash so the button can report fields that landed a moment earlier. `applySetting('meticulousHost')` updates `#meticulous-addr` and reconnects.

## Shot persistence (v0.8)

Record of truth is IndexedDB (`shots` store). Lifecycle of a live shot:

1. `extracting` rises → `ShotRecorder` starts; every `sample` event calls `checkpointLiveShot()`, which at most every 2 s writes a snapshot `{…shot, inProgress: true, checkpointAt}` under the shot's final id. The first checkpoint makes the row appear in History as "recording now…".
2. Pump stops → settle window → `shot` event. The handler awaits any checkpoint write still in flight, then overwrites the id with the finished record (`inProgress` removed). Too-short recordings delete their checkpoint instead.
3. `autoSaveFiles` (default on): JSON + CSV written to `<folder>/portal-met-bridge/shots/<base>.json|csv` via `log.saveFile`; `shot.files = {json, csv, at}`. Repeated after the machine record attaches (same names, overwritten).
4. `autoAttach`: after `attachDelaySec`, `/history/last` is matched by time (±45 s) and swapped in. Shots that still lack `machineSource` after 7 days-worth of lookback get `backfillMachineRecords()` 1.5 s after every machine connect: `POST /history` (60 newest, no data) → match by time → `shotById` for the data.
5. On start, `recoverUnfinishedShots()` runs `finalizeCheckpoint()` over any `inProgress` rows (pure, in `recorder.js`): duration = last sample time, `recovered: true`, `endedAt = checkpointAt`. Fewer than 5 samples → dropped.
6. `beforeunload` warns while recording and fires one last best-effort checkpoint.

History (`renderHistory`) is a plain sorted/filtered render of `state.shots` (the `listShots()` result, 200 newest); TDS column = reading, else `estimateShot()` over the cached analysis summary. Edits go through `openShotDialog/saveShotDialog`, deletes through `deleteShots()` + `confirmDialog()`. The "This coffee" fields write into the selected shot only while it is the newest one.

## Beverage weighed vs. machine weight (v0.8.2, reworked in v0.10)

`shot.finalWeightG` is what the machine's scale reported (max cup weight during the shot) and is never edited. `shot.beverageG` is optional: the cup weight the user measured on their own scale, entered in History → Edit or with a refractometer reading. `beverageOf(shot)` (analysis.js) is what yield, EY, the ratio, the summary CSV (`beverage_g`, next to `beverage_source`, `profile_target_g` and `machine_weight_g`), the PDF and the Beanconqueror `beverageOut` use. The History row marks a value other than the scale's with ⚖ (weighed) or ◎ (profile target), tooltip showing the scale's value; the Shots header says "41.5 g out (weighed; machine 40.0 g)". Analysis and calibration stay in machine-mass space: EC is integrated against the scale's curve, not the hand weight.

Up to v0.9 a cup weighed together with a reading was stored only as `refractometer.beverageG`, and `beverageOf` fell back to it. v0.10 drops that: `store.promoteLegacyBeverage()` runs once (`beveragePromoted` setting) and copies such values to `shot.beverageG` when they differ from `finalWeightG` by ≥ 0.25 g (equal values were the app's own fallback, not typed). New readings store only `tdsPct`, `eyPct` (a snapshot) and `at`; `measuredEy(shot)` recomputes EY from the current beverage wherever it is shown, so switching the beverage default never leaves a stale EY.

## Final weight: id-based targets, the manual mode, review exports (v0.12)

Why 38 g showed up for a 43 g profile: `applyProfileTarget` looked the target up **by profile name**, and the machine allows several profiles with one name (`Blooming Espresso` existed with 38 g and 43 g). v0.12: the status stream's `id` (the loaded profile's id, set by `backend.py` next to `loaded_profile`) is kept on the shot as `profileId`; `refreshProfileTargets` builds `state.profileTargetsById` and a by-name map whose value is `NaN` when a name maps to different targets; `applyProfileTarget` uses the id first, a unique name second, and otherwise waits for the record (`shot._targetAmbiguous`, logged once). `attachMachineRecord` uses `profileFinalWeight(saved.profile)` (analysis.js): the `final_weight` field, a `$variable` reference in it, or a weight variable (key/name says final weight / yield / output / target), with the machine's `≥ 2000 = no weight stop` sentinel treated as null; it also stores `saved.profile.id`. The mock has a second "Blooming Espresso" (`dup00002`, `final_weight: "$final_weight"` → 38 via a variable) and sends `id` in its status.

The digest tells the model which figure is which: `meta.beverageG` (the cup), `meta.weighedG`, `meta.scaleFinalG`, `meta.profileTargetG` and a `meta.beverageNote` sentence (`beverageNoteFor`), and the template rule says never to present the target or the scale as the measured yield when a hand-weighed value exists.

`beverageDefault` gained `'manual'` (`BEVERAGE_PREFERENCES`): `beverageSource` returns null unless `shot.beverageG` is set, so `beverageOf` is null, ratio/EY blank, History shows a *? g* link (`data-act="weigh"`), the Shots header says "final weight not entered" with an *Enter final weight* button, and the recorder's save opens `#weight-dialog` (`openWeightDialog` / `saveWeightDialog`; Enter saves; a blank clears). The Settings copy now says *Final weight* with the three sources.

Review exports: `js/review-export.js`. `parseMarkdown`/`parseInline` (moved into review.js; `renderMarkdown` and `markdownToText` are writers over the same blocks) → `reviewMarkdownFile` (header + text), `reviewToDocx` (a .docx zip written by hand with fflate: `[Content_Types].xml`, `_rels/.rels`, `word/document.xml`, `word/styles.xml` with Title/Subtitle/Heading1–3/Quote/Code/Footer, `docProps/core.xml`; lists as indented paragraphs with text markers, tables with a shaded repeated header row and proportional `gridCol` widths; verified with python-docx and a LibreOffice render), `reviewToPdf` (jsPDF, loaded on demand via `export.js`'s `loadJsPdf`: rich-text word layout with per-run fonts, wrapped table cells, page breaks, page numbers; `pdfSafe` spells out the symbols Helvetica lacks — → ∫ µ ≥ …), `reviewFile(rev, fmt, { jsPDF })`. Setting `reviewFormat` (md default) presets `#an-format` and each saved row's `select.fmt`; `downloadReview(rev, fmt)` → `deliver(name, data, mime, 'reviews')`.

## Before the review: the profile read and the final weight confirmed (v0.13)

A review was only as good as what the shot happened to carry: a live-only shot had a profile *name*, a shot brewed with one of two same-named profiles had the record's target, and the final weight came from Settings without anyone looking at it. v0.13 puts a confirmation step between ticking shots and *Review with AI*: `#an-preflight` renders one `.pf-row` per ticked shot (`renderPreflight`, state in `an.pending` / `an.confirmed`; `allConfirmed()` gates `#an-run` and `runReview` refuses otherwise), and every change of ticked shots resets the confirmations.

**Profile.** The picker's first option is the record (`reviewProfileOf(shot)` = `shot.reviewProfile || shot.machineSource.profile`), labelled *As recorded* / *Chosen earlier* / *Name only*; the rest is `state.profileList` (from `/api/v1/profile/list`, already fetched for the brew controls) with target and temperature. Choosing a machine profile fetches it in full with `meticulous.profile(id)` → `GET /api/v1/profile/get/<id>` (the list endpoint omits stages unless `?full=true`; `meticulous.profiles({ full: true })` exists too) into `state.profileFull`, and `profileLine()` shows what the review will read: `profileFinalWeight`, `temperature`, each variable with a unit from its `type` (time → s, flow → ml/s, pressure → bar, weight → g, temperature → °C) and the stage names. *Confirm* stores `shot.reviewProfile = compactProfile(full)` (+ `.id`), `profileName`, `profileId`, `profileTargetG`, `profileTemperatureC`; going back to *As recorded* deletes `reviewProfile` and restores the record's values. `buildShotDigest(shot, analysis, { profile })` defaults to `reviewProfileOf(shot)`; `meta` gains `profileChoice` ("as recorded by the machine for this shot" / "chosen by the user for this review" / "name only (no record attached)"), `profileTemperatureC`, `profileVariables`, `profileStages`, and `recordedProfile` (name, target, temperature of the record when a different profile was chosen, so the model can say "the record says 38 g, the profile you chose 43 g"). The prompt's `profile` object is the chosen one (`prepareReview` → `compactProfile(reviewProfileOf(shot))`).

**Final weight.** Radios *weighed by hand* / *the profile's target* / *the machine's scale* / *other* (typed), each with its value, disabled when the shot has no such value, preselected from `beverageSource(shot)`. Confirming a typed value sets `shot.beverageG` (so it is "weighed" from then on, the ⚖ in History); confirming *profile* or *scale* deletes `beverageG` and sets `shot.beveragePrefer` — a **per-shot pin** that `beverageSource` honours before the Settings default (`BEVERAGE_PREFERENCES` values; an explicit `prefer` option still wins, an unknown pin is ignored). A typed field keeps focus while it un-confirms the row (`markUnconfirmed` edits the row in place instead of re-rendering). The EY is recomputed, `analysisCache` dropped, the shot stored and its files rewritten.

The mock machine serves `/api/v1/profile/get/<id>` and `/api/v1/profile/list?full=true` for its four profiles (`80c5ea87` 43 g 92 °C with bloom_time 20 s and extraction_flow 2 ml/s; `1a830a13`; `demo0001`; `dup00002` with `$final_weight`), with `stagesFor()` building stage lists.

## Profile target as the beverage (v0.10)

The machine stops the pump at the profile's `final_weight`, so the cup ends at that target plus drips; the scale's reading during the shot misses the drips and is noisy. `beverageSource(shot)` resolves `'weighed'` (`beverageG`) → `'profile'` (`profileTargetOf(shot)`, when the module preference is `'profile'`) → `'scale'` (`finalWeightG`) → `'profile'` again if the scale has nothing. `setBeveragePreference('profile'|'scale')` is the module-level switch fed by the `beverageDefault` setting (`#set-beverage-default`, Settings → Recording → Beverage weight; default `'profile'`); since export.js and beanconqueror.js import the same module instance, the hand-off and CSV follow automatically. `beverageDefaultOf(shot)` is the resolution ignoring `beverageG`, used for placeholders and the EY of a blanked field.

`profileTargetOf(shot)` reads `shot.profileTargetG`, else `shot.machineSource.profile.final_weight` (so every earlier shot with its record attached gets the target without a migration). `profileTargetG` is stamped in three places (main.js): at the recorder's `recording` state from `state.profileTargets` — a `Map` name → `final_weight` filled by `refreshProfileTargets()` from `GET /api/v1/profile/list` on every machine connect and whenever a name is missing (the profile name itself can arrive a few status packets late, so the `sample` handler re-applies); at the final save as a last chance; and in `attachMachineRecord()` from `saved.profile.final_weight`, which is what was actually brewed and so overrides the list. The live header shows "Profile: X · target 38.0 g" once known. `tests/mock-meticulous.mjs` brews a 38 g target while its demo shot's scale ends at 40 g so the two are told apart in the e2e.

## Grind column (v0.10)

`context.grindSize` is stored as the string the forms build ("420 µm"); `grindMicrons(context)` (analysis.js) parses it (also bare numbers) for the sortable History column (`data-sort="grind"`, after Profile) and the search haystack.

## AI review (v0.11)

`js/review.js` does everything deterministic so the model interprets rather than computes. `buildShotDigest(shot, analysis)` splits the machine samples into stages by the `status` name the machine sends with every sample (`splitStages`; idle / click to start / heating / retracting are not stages, and the first retracting sample marks the pump stop), and for each stage reports time span, water in (∫ flow dt, as the hand-off does), cup start → end and rate, pressure start / max (and when) / end / slope, mean and max flow, water temperature start → end, EC at the boundaries (Portal time shifted by the shot's lag); then first drop (cup ≥ 0.5 g), pump stop, drips after the pump, total water, water before the first drop, temperature start / min / max / end, and — when the Portal was there (≥ 10 samples and a weight curve) — the EC summary: mean EC/g, ∫EC dm, peak and where, final EC, coverage, mass at 90 % of the integral, the last-5 g tail, the Portal's outlet temperature, and the share of ∫EC dm by stage end and at 5 g cup-mass milestones (from `analysis.curve`). A `gaps` list names what is missing (no dose, no grind, no machine samples, **no Portal data**, no temperature, record not attached), and a `series` table gives one row per second (t, pressure, flow, cup, temperature, EC). Shots without Portal data go through the same path with `ec: null`, so the review falls back to the machine's data by design. `compactProfile()` strips the record's profile to name, temperature, final weight, description, variables and stages (dynamics, exit triggers, limits) — no image, no ids.

`buildReviewMessages(shots, options)` returns `{ system, user }`. The system prompt is the method of the "Meticulous espresso profile review" query (read the setup → stage by stage against the profile's design → where the extraction happened → cross-check the records → judge → recommend one change per shot in grinder steps; several shots → series first) and the report template taken from the Shot review doc (Verdict · Shots compared · Stages table · What stands out · Suggested changes · Open questions · Sources, with the rules: use the digest's numbers, never invent, no title/preamble, don't describe the chart). The user message carries the grinder step, usual drink, standing notes, taste, question, and per shot the gaps, the digest JSON (minus the series), the profile JSON and the series JSON. `approxTokens` (chars ÷ 3.6) feeds the size note. `renderMarkdown` is a small escaping renderer (headings shifted down one level, lists with one nesting level, tables, code, blockquotes, bold/italic/code, http(s) links only).

`js/ai.js` holds the three providers: `buildRequest` (Anthropic `/v1/messages` with `anthropic-dangerous-direct-browser-access: true`, OpenAI `/v1/chat/completions`, Gemini `:streamGenerateContent?alt=sse` with `x-goog-api-key`; **no `temperature`/`top_p` unless passed explicitly** — v0.11.2, after Opus 5.5 answered `400 · \`temperature\` is deprecated for this model`; the current reasoning models on every provider refuse sampling knobs, and a review does not need them), `isParamRejection` + `stripOptionalParams` (a 400 whose message names a sampling parameter → the same request once more without `temperature`/`top_p`/`top_k`, also inside Gemini's `generationConfig`; any other 400, or a second refusal, is reported as is; `onRetry` lets the app log it), `deltaFromEvent` per provider, `makeSseParser` (events split on blank lines, multi-line `data:` joined), `streamCompletion` (falls back to a plain JSON body when the response is not an event stream), `listModels` + `normalizeModelList` (text models only, newest first; OpenAI-compatible servers keep their own ids), `testKey` (a one-word reply), `maskKey`. Defaults: `claude-sonnet-5-5`, `gpt-6.1-sol`, `gemini-3.8-flash`; the OpenAI base URL is overridable (`aiBaseOpenai`) for OpenRouter / local servers, which is also how the e2e drives the mock (`tests/mock-meticulous.mjs` answers `/v1/models` and `/v1/chat/completions` with SSE and echoes the shot count and the no-Portal flag it saw in the prompt).

Settings: `aiProvider`, per provider `aiKey…` (`secret: true` → masked in the log, excluded from `settingsDocument()`), `aiModel…`, `aiBaseOpenai`, `aiGrindStepUm`, `aiDrink`, `aiNotes`; all in the `SETTINGS` table so the save bar, Enter/⌘S and import/reset apply. Keys live only in IndexedDB `settings`. Saved reviews are a new `reviews` store (DB v4: `{ id, createdAt, title, shotIds, shotLabels, provider, model, taste, question, markdown, digests (no series), durationMs, app }`), included in `exportAll()/importAll()` and the erase dialog. The Analysis view (`an` state in main.js): picker over `state.shots`, digest tables + a second `TimeChart`, streamed Markdown re-rendered every 150 ms, Stop (AbortController), Save/Download/Copy, saved list with Open/.md/Delete. History's *Analyze selected* calls `openAnalysis(ids)` (≤ 8).

## Brew from the app (v0.11)

`meticulous.action(name)` → `POST /api/v1/action/<name>` (backend `api/action.py`: ESP actions `start, stop, tare, scale_master_calibration, preheat, continue, finish, home, purge`, backend actions `reset, abort`; 409 when the ESP refuses — busy or a motor-strain alarm — 400 with `allowed_actions` otherwise; `abort` answers with an empty body). `start` is the dial click: from idle the backend sends the last loaded profile to the ESP and the compiled profile's own "click to start" stage waits for a second click, unless the machine's `auto_start_shot` setting skips it. `abort` runs `Machine.end_profile()` — `home` during a shot (piston retracts), `stop` otherwise — which is why the Stop button uses it. `meticulous.loadProfile(id)` → `GET /api/v1/profile/load/<id>` (409 while busy). The rail's Brew block appears on connect, lists `state.profileList` (kept by `refreshProfileTargets`), follows the status stream (`renderBrewState`: "click to start" → *Start brew now*), and never sends anything on its own. The mock plays idle → heating (0.8 s) → click to start on `start`, back to idle on `abort`/`stop`, and records the actions at `/mock/dial`.

## Ratio and compare (v0.9)

`ratioOf(shot)` = `beverageOf(shot) / context.doseG` (null without a dose) feeds the History column, the shot header, the compare legend and the summary CSV (`ratio`). Compare (`openCompare(ids)` in main.js, `CompareChart` in charts.js) overlays up to eight ticked shots (`COMPARE_COLORS`) on one uPlot: series are aligned with `uPlot.join` and drawn with `spanGaps`, so the x grid is the union of every shot's x values. Graph choices are in `COMPARE_SERIES` (mass-based: EC and ∫EC dm from `analyzeShot().curve`; time-based: EC from the Portal samples, cup weight / flow / pressure from the machine samples). For mass-based graphs the x-axis can be grams or brew ratio (x ÷ dose); shots without a dose are listed but not drawn in that view. The chart is rebuilt on every change — the series count varies and uPlot construction is cheap.
